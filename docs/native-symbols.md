# Native PDB symbols

TraceRender has one native resolver for CPU and allocation stacks. `NativeSymbolResolver` uses LLVM's Native PDB reader locally. It does not use DIA, DbgHelp, a Windows helper, a symbol server, or automatic downloads.

Pass local PDB files, matching EXE/DLL files, or directories to the constructor. The desktop importer reads native MSF/PDB resources embedded in a .diagsession directly into the same resolver with `add_embedded_pdb`, without extracting files to disk. Their filenames may be arbitrary. Directories are searched for the captured `ProfileModule.pdb_path` basename, then the captured binary basename. If no PDB path was recorded, the module basename with a `.pdb` extension is used. Searches are not recursive. Set these paths in Settings > Symbols, one path per line, then reopen the capture.

The resolver requires `ProfileModule.build_id` to contain the captured `GUID/decimal-age`. GUID braces, hyphens, and case do not affect matching. It checks the candidate PDB's own GUID and age, including when LLVM finds a PDB through a supplied binary. A filename, release label, binary image size, or supplied binary alone never establishes the captured build. Missing or mismatched identity leaves the address unresolved.

`resolve(module, address, observation_ts)` checks the captured address range and, when provided, the observation time against `[load_ts, unload_ts)`. The decoder must bind every frame to the correct explicit module and process lifetime. `resolve_profile(model, progress)` consumes those bindings in the common stack-frame table, so CPU and allocation stacks use the same symbols. It does not guess module ownership from an address reused by another process or load. Original addresses, module identities, and load bases remain in the model.

Resolved identity is the module-lifetime ID plus the function RVA. Different instruction addresses inside one function share that identity; identical names in different module lifetimes do not. Unresolved frames retain module offsets and an address identity. Flame and range aggregation uses native identities when supplied. Chrome samples without native identities keep their existing name-based behavior. Text search still searches names.

The resolver caches successful PDB sessions, failed candidate opens, and individual RVA lookups for its lifetime. Create a new resolver after changing symbol paths or replacing files. Existing saved resolutions survive reopening even when no local symbols are available. File/line metadata feeds the existing Source panel and path-remapping settings; source code itself is not embedded. Unresolved results add deduplicated profile-quality warnings.

## Build and packaging

`TRACE_RENDER_NATIVE_PDB` defaults to `ON`. CMake enables it only if a local LLVM 18.1 development package is found. For a nonstandard installation:

```sh
cmake -B build -DLLVM_DIR=/usr/lib/llvm-18/lib/cmake/llvm
cmake --build build
```

The build links LLVM's `DebugInfoPDB` component and its dependencies. LLVM include directories apply only to the resolver translation unit. No LLVM source or toolchain is downloaded by the project. Package the resulting binary with any dynamic dependencies reported by the target platform's dependency inspector. Ubuntu's tested component libraries are static; system compression/support libraries may remain dynamic. Other LLVM minor versions have not been validated.

Disable the backend explicitly with `-DTRACE_RENDER_NATIVE_PDB=OFF`. Builds without the development package and WebAssembly builds retain the same resolver API, returning unresolved module offsets and an unavailable-backend diagnostic. Already-resolved `.trprofile` files still open.

## Verified support and limits

The tested backend reads full native MSF/PDB files generated by MSVC and LLVM's COFF linker, and resolves function records plus available source lines. Matching full PDBs can supply section information without an EXE. A supplied binary can help LLVM locate its associated PDB, but does not bypass captured-identity verification.

A function record must cover the requested RVA. Public symbols without a known function extent resolve only at their exact start address; padding and unknown ranges remain unresolved. Portable managed PDBs, missing object data from partial/FASTLINK builds, reconstructed inline stacks, and binary-only export symbolication are outside this implementation. Missing source lines do not invalidate a known function name.

Offline tests use [the original fixture](../tests/fixtures/native_symbols/README.md), a 72 KiB PDB and 2.5 KiB EXE built on Linux without a Windows SDK. They cover exact matches, wrong GUID/age, unavailable identities, missing and corrupt candidates, renamed embedded resources, binary candidates, module lifetimes, cached lookups, save/reopen, and separate same-name function aggregates.

The production resolver was also verified against the public OBS CPU capture and the matching Qt6Widgets PDB from the [OBS Qt symbol archive](https://github.com/obsproject/obs-deps/releases/download/2025-08-23/windows-deps-qt6-2025-08-23-x64-PDBs.zip). Captured GUID `1A6ED01C-6CE2-40AE-8959-60A52DAEBE62`, age `1`, load base `0x7ffbd1560000`, and captured image size `0x62c000` resolve:

| Captured RVA | Function | Source line |
|---|---|---|
| `0x5495c` | `QWidgetPrivate::drawWidget` | `qwidget.cpp:5658` |
| `0x5e3f6` | `QWidgetPrivate::paintSiblingsRecursive` | `qwidget.cpp:5794` |
| `0x12056` | `QApplication::notify` | `qapplication.cpp:3250` |

That optional integration check does not download files:

```sh
TRACE_RENDER_OBS_SYMBOLS=/path/to/extracted/pdbs ./build/trace_render_tests \
  --gtest_filter=NativeSymbols.AuthenticObsQtAddressesResolveWithCapturedIdentities
```
